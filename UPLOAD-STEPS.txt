PUTTING A HOME BINGER UPDATE ON GITHUB (about 10 minutes, free)
===============================================================

You have: this zip = the complete, ready-to-commit source for this
release. (The .gitignore inside already keeps out runtime data, test
media, and builds — nothing to configure.)

FIRST TIME ONLY — create the repo
---------------------------------
GitHub Desktop (desktop.github.com) → File → Add Local Repository →
pick the extracted folder → it offers to create one → name: home-binger,
Git ignore: NONE, License: NONE (both already included) → Publish.
Private is fine; flip to public later in repo Settings.

EVERY UPDATE — three drags
--------------------------
1. On github.com, open your repo → "Add file" → "Upload files" → drag
   EVERYTHING from inside this zip in (matching files get replaced).
   Commit message: a one-liner like "1.9.0".
2. Releases (right column) → "Draft a new release".
3. Tag: v1.9.0        <- plain "v" + the version number, no extra letters
   Title: Home Binger 1.9.0
   Notes: paste the release-notes file delivered next to this zip
   (RELEASE-NOTES-v1.9.0.md).
   Drag the exe zip (HomeBinger-1.9.0-beta.zip) into "Attach binaries",
   then Publish. Do NOT tick "Set as a pre-release" — the app's update
   notice only looks at regular releases.

WHY THE TAG MATTERS
-------------------
Every copy of the app checks this release's TAG on launch and shows a
"new version out" note when the number is higher. Plain v1.8.1 parses
cleanly. (Tags with letters in front, like "Rv1.8", used to hide the
note — 1.8.1 tolerates them, but plain v-tags keep it simple.)

ONE CHECK BEFORE GOING PUBLIC
-----------------------------
The rights-encumbered test media must not be in the commit:

    git ls-files | grep tests/media

must print NOTHING. (.gitignore excludes it — this just proves it.)
