PUTTING HOME BINGER 2.1 ON GITHUB (about 10 minutes, free)
===========================================================

You have: this zip = the complete, ready-to-commit source for this
release. (The .gitignore inside already keeps out runtime data, test
media, and builds — nothing to configure.)

WHERE THINGS STAND RIGHT NOW
----------------------------
The repo's latest public release is "2.0-beta" (2026-10-12). Publishing
v2.1 as a REGULAR release (pre-release box NOT ticked) makes the
"new version out" notice appear for everyone still on 1.15, 1.10.1,
1.10 and older — that is the point of this release. 2.0 brought the game room,
watch parties and keyless music; 2.1 sharpens the watch-party picture
(raised quality ceilings + the Ultra tier).

THE VERSION SCHEME (owner's call, 2026-10-12)
---------------------------------------------
  2.1      this release
  2.x      updates and bug fixes (tag them v2.1, v2.2, …)
  3.0      the library megaproject, when it lands
The app reads its own version from package.json — the sidebar badge
and the new-version notice both follow it automatically. Nothing to
hand-edit in the app, ever.

EVERY UPDATE — three drags
--------------------------
1. On github.com, open your repo → "Add file" → "Upload files" → drag
   EVERYTHING from inside this zip in (matching files get replaced).
   Commit message: a one-liner like "2.1".
   (First push of this release also fires the "Watch page" workflow —
   that publishes the browser guest page for watch parties. It's
   already enabled: Settings → Pages → Source "GitHub Actions".)
2. Releases (right column) → "Draft a new release".
3. Tag: v2.1           <- plain "v" + the version number, no extra letters
   Title: Home Binger 2.1
   Notes: paste RELEASE-NOTES-v2.1.md (it's in this zip, repo root).
   Drag the exe zip (HomeBinger-2.1.0.zip) into "Attach binaries",
   then Publish. Do NOT tick "Set as a pre-release" — the app's update
   notice only looks at regular releases.

WHY THE TAG MATTERS
-------------------
Every copy of the app checks this release's TAG on launch and shows a
"new version out" note when the number is higher. Plain v2.0 parses
cleanly. Keep tags plain (v2.1, v2.2, v3.0) — letters in front (like
the old "Rv1.8" and "V1.8.8.8") used to hide the notice.

TAG CLEANUP (optional, one minute, recommended)
-----------------------------------------------
The tag list has two malformed leftovers from early days: "Rv1.8" and
"V1.8.8.8" (capital V, four segments). They look like typos to
visitors. To remove: repo → Tags (under Releases) → find each → the
trash icon. (If a release is attached to them, delete the release
first — v1.8.8.8 and Rv1.8 have no releases attached, so it's just
the two clicks.)

ONE CHECK BEFORE GOING PUBLIC
-----------------------------
The rights-encumbered test media must not be in the commit:

    git ls-files | grep tests/media

must print NOTHING. (.gitignore excludes it — this just proves it.)
